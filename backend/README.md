# Mandate backend

Backend-only implementation aligned to `../MANDATE_ARCHITECTURE.md`. No frontend is included.

## Current phase

Implemented slices: (1) policy/domain foundation; (2) PostgreSQL schema/migrations; (3) REST identity and agent registration; (4) immutable draft policy/revision writes; (5) deterministic agent action evaluation with atomic budget/nonce reservation; (6) exact-action human approval/denial; (7) read-only policy simulation and tenant-scoped activity reads; (8) an outbox worker and alert feed; (9) model-provider BYOK credential lifecycle; (10) a first Safe transaction/module guard plus agent-signature execution module for local EVM execution; (11) paused-by-default account registration and verified Safe enrollment; (12) a separate finalized-block EVM log indexer with durable cursor and common-ancestor reorg rollback; (13) finalized protection-loss events that pause accounts and create durable audit/alerts; (14) a typed EVM policy compiler that converts only the contract-enforceable native/ERC-20 subset into exact `configurePolicy` calldata; (15) an owner-only persisted Safe activation-plan endpoint with exact EIP-712 transaction payloads; (16) finality-aware Safe receipt verification that atomically activates the matching policy and grant; (17) owner-only persisted Safe revocation planning and finality-verified atomic policy/grant revocation; (18) a tested exact-action EIP-712 authorization planner for native/ERC-20 transfers; (19) a pinned-block EVM state reader that checks Safe/guard/module links, agent key state, and module nonce; (20) an agent-only, tenant-scoped authorization endpoint that persists an immutable exact-action authorization, `AUTHORIZED` execution attempt, action transition, hash-linked audit event, outbox event, and idempotency result atomically; and (21) strict EIP-712 agent-signature verification plus validation of the outer agent-signed transaction against the exact authorized Safe-module call, with an EVM RPC broadcaster that uses only the caller's signed raw transaction and never a Mandate-controlled private key. The signature checker enforces the contract's 65-byte, low-s, `v=27/28` requirements; the transaction validator checks sender, chain, module destination, zero outer value, gas limit, and exact calldata. The configured-chain broadcaster is proven against local Anvil/Safe. Phase 22 wires these primitives to an agent-only `/execute` route, validates caller-signed bytes before broadcast, records an immutable per-action transaction hash/idempotency claim without retaining raw bytes, and atomically transitions the action/attempt/authorization to `SUBMITTED` with audit and outbox events after broadcast. Uncertain RPC outcomes retain a `PENDING` hash-only claim so a retry can rebroadcast only the identical signed transaction. Phase 23 adds worker-driven tentative/final receipt reconciliation, receipt-reorg observations before finality, hash-linked audit/outbox updates, and exactly-once reservation consume/release on final success/revert; Phase 24 resolves fee-replacement transactions when the finalized indexer contains the exact `AgentActionExecuted` event for the stored agent, key version, module nonce, and typed action hash; Phase 25 classifies a submission as DROPPED only when its stored caller-signed outer sender/nonce was consumed at a hash-verified finalized checkpoint after authorization expiry, complete indexer coverage spans the authorization snapshot, and no exact execution event exists; it atomically records DROPPED → RECONCILED, releases the reservation, and writes audit/outbox evidence. Legacy submissions without these proof fields or known indexer start boundaries remain pending. Phase 26 periodically rechecks settled receipts against a hash-verified, newly finalized canonical block and an independently finalized indexer row; a verified post-finality block replacement moves receipt/attempt/action to `REORGED`, reactivates the reservation as a budget hold, pauses the affected account, and writes one incident audit/outbox event. Phase 41 adds the owner recovery route: an OWNER chooses `CONSUMED` or `RELEASED` with a reason and optional evidence hash. Resolution is immutable, idempotent, and audited; it only updates the reservation. Action/attempt/receipt remain `REORGED` and the account remains `PAUSED` pending separate verification. Phase 27 adds durable webhook-delivery rows seeded transactionally from selected outbox events, HMAC-SHA256 signing, bounded retries, secret-manager retrieval, HTTPS-only public-address validation at connection time, redirect rejection, and nested sensitive-field filtering. Phase 28 adds authenticated OWNER/ADMIN webhook management routes, SSRF-validated creation, idempotent enable/disable/delete, one-time 256-bit signing-secret provisioning/rotation, retained delivery history, and hash-linked audit/outbox events. Phase 29 adds tenant-scoped team membership listing, role assignment/removal, OWNER-only ownership changes, last-owner protection, idempotency, and audit/outbox recording. Phase 30 adds a local MCP stdio process with identity-pinned typed policy/action/receipt tools over the authenticated REST API. Phase 31 adds authenticated, idempotent organization creation with atomic initial OWNER membership and audit/outbox records. Phase 32 adds invitation-token creation and verified-email acceptance with token hashes, expiry, idempotent replay, and audit/outbox records. Phase 33 adds tenant-admin invitation listing and idempotent revocation with transactional state/audit/outbox updates; Phase 34 adds opt-in OpenTelemetry; Phase 35 adds shared PostgreSQL API rate limiting; Phase 37 adds SDK and CLI foundations; Phase 39 adds invitation administration; Phase 40 adds hosted Streamable HTTP MCP and resource-audience validation. Secret cleanup is tracked across provider failures. The REST process exposes health, OpenAPI, authenticated `/api/v1/me`, tenant-scoped accounts, agents and policies, draft/revision creation, activation and revocation planning/finalization, policy simulation, action submission/approval/authorization/execution/detail and deep-reorg resolution, audit events, reconciled receipt listing, alerts, and `/api/v1/orgs/{orgId}/integrations/model-providers` credential endpoints. Human requests require RS256 JWTs verified against a configured OIDC JWKS URL; membership and role checks are repeated in transactional write paths. Agent bearer secrets are random, returned once, stored only as SHA-256 hashes, and bound to one tenant/agent/key version. Action submission atomically records its lifecycle, decision, reservation (when allowed/held), nonce counter, audit events, outbox event, and idempotency result. Human decisions bind to the stored exact action hash, prohibit the policy author from approving that action, and atomically move/release/expire its reservation. Simulation reuses the deterministic evaluator and budget reads without creating action, reservation, audit, or nonce changes. Model keys are accepted only on the server-side authenticated integration route; PostgreSQL retains only provider, masked suffix, status, timestamps, and a Secrets Manager ARN/reference. `ModelProviderRuntime` resolves an active key through the secret-store port for server-side runtime use; no HTTP route returns the raw key to the browser or agent. The connection test performs a bounded, fixed-provider models-list request (no inference prompt). Action detail, audit feed, and receipts are filtered by tenant and agent principal; receipt listing now projects reconciled on-chain evidence from the shared receipts table. Real PostgreSQL integration tests cover these flows.

The outbox worker claims events with `SKIP LOCKED`, projects safe event categories into an idempotent PostgreSQL alert-notification table, marks delivery atomically, and releases failed events with capped exponential retry timing. It also seeds matching webhook deliveries in the same transaction. The webhook delivery worker signs JSON bodies with HMAC-SHA256, uses one stable delivery ID across retries, caps attempts at 12, and stores only coarse error codes. It retrieves signing keys through the secret-manager port and connects only to validated public HTTPS destinations without following redirects; sensitive field names are filtered from event payloads. Run it separately with `npm run dev:worker`. Provider-key and webhook-secret storage use AWS Secrets Manager and the AWS SDK default credential chain, with optional `AWS_REGION` / `AWS_DEFAULT_REGION`; the production IAM role needs narrowly scoped create/get/delete access under `mandate/model-providers/*` and `mandate/webhooks/*`. AWS/KMS account wiring and live cloud verification remain deployment tasks. EVM accounts can be registered/listed through authenticated tenant routes; registration transactionally persists a PAUSED record plus audit/outbox entries. `POST /api/v1/orgs/{orgId}/accounts/{accountId}/verify` queries the configured chain RPC, validates the Safe contract, paired guard slots, guard-to-Safe link, configured module, module-to-Safe/guard links, and Safe module enablement against one pinned block snapshot, then atomically records the verified guard/module and activates the account. The API process accepts server-only `MANDATE_EVM_RPC_URLS` as a JSON map from chain ID to HTTPS RPC URL (loopback HTTP is allowed for local testing), and `MANDATE_SAFE_SINGLETONS` as a JSON map from chain ID to the trusted Safe singleton address. The indexer runs separately as `npm run dev:indexer`; configure `MANDATE_INDEXER_START_BLOCKS` to each deployed account's/adapter's first relevant block, `MANDATE_INDEXER_CONFIRMATIONS` to a chain-qualified confirmation depth, and the bounded poll/range settings. It verifies RPC chain IDs, indexes only blocks below the confirmation head, persists block and log data transactionally, and on a changed tip searches for a common ancestor and deletes orphaned block/log rows before rescanning. Finalized Safe `ChangedGuard` events pause an ACTIVE account only when the newly configured guard differs from its enrolled guard; Mandate `PolicyRevoked`/unexpected module-change and Safe `DisabledModule` events pause matching accounts. Demotion, hash-chained audit, outbox alert, indexed logs/blocks, and cursor advance commit in one transaction; the worker projects the event into an “Account protection paused” alert. Paused accounts require owner/admin re-verification before returning ACTIVE. Reorg rollback removes orphaned indexed log records but deliberately does not auto-reactivate a paused account; recovery uses the account verification endpoint. Execution receipt projection/reconciliation is implemented in Phase 23; Phase 24 recovers exact canonical fee replacements; Phase 25 adds proof-bound dropped settlement; Phase 27 adds signed webhook delivery plumbing and Phase 28 adds authenticated webhook endpoint lifecycle management. The Safe guard/module executes and enforces only native/ERC-20 transfer calls in a real Safe v1.5.0 proxy on local Anvil; both transaction and module guards must be installed, and signatures bind Safe, chain, epoch, agent key version, exact calldata/value, deadline and nonce. Phase 9 adds an owner-authorized, one-time exact-call approval threshold to the contract boundary; the approval binds Safe/chain/policy revision and epoch, agent key version and nonce, recipient, value, calldata hash, and deadline, then is consumed atomically with successful module execution. Arbitrary calls, batching, token approvals/delegation, and quotes remain unsupported. Agent caller-signed transaction submission and final receipt reconciliation are supported for the bounded native/ERC-20 transfer subset. Policy activation and revocation both use owner-Safe plan/finalization lifecycles: activation persists a PENDING grant and finalizes to ACTIVE only after the Safe transactions meet configured finality; revocation leaves the policy/grant ACTIVE while owners execute the exact `revokePolicy()` Safe transaction, then verifies its finalized receipt and resulting disabled guard epoch before atomically marking both REVOKED. The backend architecture remains incomplete and is not production ready: identity-provider account provisioning, remaining CLI command families/package release, AWS anchor-bucket provisioning and live cloud verification, and full Phase F production deployment/incident qualification remain. Receipt reconciliation can recover successful/reverted fee replacements from the finalized exact-action module event and classifies a drop only with finalized sender-nonce, expiry, indexer-coverage, and exact-event-negative evidence; legacy records without proof metadata remain pending. It detects a deep reorg after the configured finality boundary, holds the reservation, and pauses the affected account; Phase 41 adds owner-only resolution of that held reservation while leaving the action/attempt/receipt REORGED and the account PAUSED. A DB reservation or `RESERVED` state alone is not execution-boundary enforcement. Frontend remains intentionally excluded.

## Requirements

- Node.js 22 or later
- npm 10 or later

Install and verify from this directory:

```sh
npm install
npm run test:coverage
npm run typecheck
npm run build
```

Start local PostgreSQL using Docker Compose (`docker compose up -d postgres`) or a local PostgreSQL 17 installation. Copy `.env.example` to `.env.local`, set `DATABASE_URL`, `MANDATE_JWT_JWKS_URL`, `MANDATE_JWT_ISSUER`, and `MANDATE_JWT_AUDIENCE`, then run `npm run db:migrate` and `npm run dev:api`. The JWKS URL must use HTTPS except for loopback development. Apply migrations only with a deployment role that owns the Mandate schema. `.env.local` is ignored by git. The model-provider key is optional and is not used by the authorization path. Production key storage requires AWS Secrets Manager credentials and least-privilege IAM; integration tests use an in-memory test adapter. Keys are never returned on reads or stored in PostgreSQL. Configure the SDK runtime region using `AWS_REGION` or `AWS_DEFAULT_REGION`.

### Containerized local backend

`Dockerfile` builds the TypeScript backend in a Node.js 22 build stage and runs the compiled API, worker, indexer, or hosted MCP entrypoint as the non-root `node` user. The root filesystem is read-only for API/worker containers; Compose drops Linux capabilities, disables privilege escalation, keeps PostgreSQL data in a named volume, binds development ports to loopback, and waits for PostgreSQL plus a successful migration job before starting the API and worker. The optional local MCP service shares the API container's network namespace so its development-only loopback API URL passes the existing HTTPS/loopback validation. This Compose stack is for local development and integration only: it intentionally uses a local password, a development HMAC key, and a placeholder OIDC issuer that will not authenticate real users.

```sh
cp .env.example .env                 # ignored by git; replace OIDC issuer/JWKS/audience
docker compose up --build -d         # PostgreSQL, migrations, API, worker
curl --fail http://127.0.0.1:3000/health/ready
docker compose logs -f api worker
docker compose down                  # retains the PostgreSQL volume
```

Set real `MANDATE_JWT_JWKS_URL`, `MANDATE_JWT_ISSUER`, and `MANDATE_JWT_AUDIENCE` values in `.env` before authenticated API use. Optional chain indexing uses `docker compose --profile indexer up -d indexer` after setting `MANDATE_EVM_RPC_URLS` and `MANDATE_INDEXER_START_BLOCKS`; hosted MCP uses `docker compose --profile mcp up --build -d api worker mcp-http` and requires `MANDATE_JWT_AUDIENCE` to include both the API audience and MCP resource URL (for local testing, `mandate-api,http://localhost:3100/mcp`). Recreate API and MCP together because this local-only profile shares their network namespace to use loopback HTTP. The indexer and MCP profiles are opt-in. Do not use `docker compose down -v` unless local database data should be destroyed. Production should use a managed/hardened PostgreSQL deployment, external secret injection, private networking/TLS, separately scoped migration credentials, pinned/scanned image digests, and the cloud qualification gates below; this local Compose file is not a production deployment template.

### Production PostgreSQL TLS

The API, worker, chain indexer, and migration command use certificate-verified PostgreSQL TLS whenever `NODE_ENV=production`. Production startup requires `DATABASE_SSL_CA_PATH` to point to a readable PEM CA bundle (for Amazon RDS, mount the current AWS RDS global bundle into the container). The clients set `rejectUnauthorized: true`; they do not support disabling verification. Do not put `sslmode`, `sslcert`, `sslkey`, or `sslrootcert` in `DATABASE_URL`, because node-postgres replaces the supplied TLS object when those URL parameters are present. Local Compose explicitly sets `NODE_ENV=development`; this exception is for its private local PostgreSQL service only. For AWS, mount the CA bundle read-only and configure the path in each database-using task.

If the API is behind an ALB or reverse proxy, set `MANDATE_TRUSTED_PROXY_CIDRS` to only the proxy subnet CIDRs and restrict the API's network ingress to the proxy security group. Forwarded IP headers are ignored by default; catch-all proxy trust is rejected. This enables the shared PostgreSQL rate limiter to distinguish clients without trusting arbitrary caller-supplied `X-Forwarded-For` headers.

For a browser frontend on a different origin, configure `MANDATE_CORS_ALLOWED_ORIGINS` as a comma-separated list of exact HTTPS origins (HTTP loopback is allowed only for local development). Wildcard and `null` origins are rejected; cookies are not enabled. The API permits only its supported methods and `Authorization`, `Content-Type`, and `Idempotency-Key` request headers. Leave the setting unset when the frontend and API share one TLS origin. Add the precise staging console origin before browser testing.

To run the complete PostgreSQL-backed integration suite inside the Compose network, create its separate test database once and start the `tests` profile (the suite applies migrations itself):

```sh
docker compose exec -T postgres createdb -U mandate mandate_test
docker compose --profile tests run --rm integration
```

To run the chain indexer, configure the RPC URL and a start block for every chain, run migrations, then start `npm run dev:indexer`. The start block must cover the deployment/account events you need indexed; the default sample is illustrative only. Optionally set `MANDATE_INDEXER_RPC_FALLBACK_URLS` to a JSON object mapping each chain ID to an ordered array of HTTPS URLs (loopback HTTP is accepted for local testing). The indexer checks each endpoint's chain ID once before use, sticks to the last healthy endpoint, and still verifies canonical block continuity and every log hash before committing; if all endpoints fail or report a different chain ID, the batch fails closed. The configured providers remain trusted RPC inputs (a matching chain ID is not a proof of canonical history), so vet provider independence before production. Indexer fallbacks only affect indexer reads; action broadcasting uses the separate `MANDATE_BROADCAST_RPC_FALLBACK_URLS` setting and retries only the exact same caller-signed bytes/hash, never a changed nonce or newly signed transaction. Choose confirmation depth according to the target chain's finality model before relying on indexed observations.

Database integration tests require a real PostgreSQL database and skip when `DATABASE_URL` is absent:

```sh
DATABASE_URL=postgresql://mandate:mandate@127.0.0.1:5432/mandate npm run test:integration
```

The unit-only `npm run test:coverage` gate requires 100% for the selected policy/domain sources. The combined source gate covers every app/package `src` file and requires PostgreSQL integration tests to run; execute it through Compose so it reaches the `mandate_test` service database:

```sh
docker compose --profile tests run --build --rm integration npm run test:coverage:all -- --reporter=dot
```

The combined gate currently requires at least 75% statements, 70% branches, 80% functions, and 82% lines across all app/package sources. CI runs unit tests, PostgreSQL/Safe/Anvil integration tests, then the combined coverage gate. Contract integration is also available through `npm run test:contracts` against local Anvil and Safe 1.5.0 artifacts. New backend phases must add tests first, observe the expected failure, implement, then run the full test, typecheck, build, database integration, and coverage suites again.

## Architecture alignment

- `packages/domain`: shared reason codes, action lifecycle, uint256 base-unit parsing.
- `packages/policy`: strict typed schemas, deterministic policy evaluator, canonical revision bytes, and revision hash.
- `packages/chain/src/evm-safe-policy-compiler.ts`: typed, exact ABI compiler for supported Safe guard policy revisions; unsupported target/selector semantics are rejected rather than weakened.
- `packages/chain/src/safe-policy-activation-plan.ts`, `packages/adapters/src/chain/evm-safe-policy-activation-reader.ts`, and `evm-safe-policy-activation-finalizer.ts`: pinned-block Safe state reads, exact EIP-712 SafeTx plans, finalized Safe success-event verification, and atomic transition of the corresponding policy/grant to ACTIVE.
- `packages/chain/src/action-execution-authorization.ts`, `packages/adapters/src/chain/evm-action-execution-state-reader.ts`, `packages/application/src/action-authorization-service.ts`, and `packages/adapters/src/postgres/action-authorization-store.ts`: pinned EVM state snapshot, exact typed authorization, agent/tenant-scoped authorization route, and transactional persistence of the authorization plus `AUTHORIZED` attempt/audit/outbox/idempotency state. Phase 22 signed submission is implemented; Phase 23 adds worker receipt finalization.
- `packages/chain/src/action-execution-authorization.ts` and `packages/adapters/src/chain/evm-action-transaction-submitter.ts`: strict recovery of the enrolled agent's EIP-712 signature, exact module calldata verification against the outer signed EVM transaction, and caller-signed raw transaction broadcasting on a configured chain. `packages/application/src/action-execution-service.ts` and `packages/adapters/src/postgres/action-execution-submission-store.ts` connect them to an agent-authenticated `/execute` route with hash-only idempotent submission tracking, retries of exact bytes, `SUBMITTED` attempt/action transitions, and atomic audit/outbox events; receipt reconciliation is provided by the worker in Phase 23.
- `apps/api`: Fastify HTTP entry point, RS256/JWKS identity verification, health checks, authenticated profile, tenant-scoped routes, and `/api/v1/orgs/{orgId}/actions/{actionId}/authorize` plus `/execute` for action-bound agent authorization and caller-signed execution submission.
- `apps/chain-indexer`: finality-depth EVM log ingestion, persisted per-chain cursor/block headers, monitored account/guard/module logs, and reorg rollback.
- `packages/adapters/src/aws/secrets-manager.ts`: server-side provider-key storage; PostgreSQL stores only secret references and masked metadata.
- `packages/adapters/src/model-provider-tester.ts`: fixed HTTPS model-catalogue authentication checks with a bounded timeout and no inference request.
- `contracts/`: Safe v1.5-compatible dual guard, EIP-712 agent module, Safe/Anvil integration test, and enforcement setup/recovery notes.
- `packages/application/src/model-provider-runtime.ts`: server-side retrieval of active provider keys for runtime callers.
- `packages/application`: agent list/register use cases and organization role authorization.
- `packages/ports`: persistence interfaces for account and agent identity records.
- `packages/api-contracts`: strict request schemas and stable error codes.
- `packages/adapters/src/postgres` and `migrations/`: PostgreSQL migration runner and source-of-truth schema, including tenant-scoped account registration and paused-on-enrollment status.
- `apps/chain-indexer` interprets the protection-loss event subset and emits durable pause/audit/outbox records. Execution receipt reconciliation is in Phase 23. Phase 27 provides outbox-to-webhook delivery plumbing; Phase 28 adds authenticated endpoint management, secret rotation, delivery history, and the OpenAPI contract; Phase 29 adds member role management with transactional owner safeguards; Phase 30 adds the local MCP stdio server and tested typed tool contract; Phase 31 adds atomic organization creation/initial-owner onboarding; Phase 32 adds expiring, token-hash-backed invitation creation and verified-email acceptance; Phase 33 adds invitation list/revoke lifecycle operations.

The evaluator is a control-plane preflight component. The local Safe guard is the account-side enforcement boundary for its documented transfer subset; the Mandate API execution coordinator independently verifies current grant state and exact signed transaction binding; it never treats an off-chain ALLOW alone as authorization.

### Organization creation (Phase 31)

`POST /api/v1/orgs` creates an organization for an authenticated human and adds that OIDC subject as its initial OWNER in one PostgreSQL transaction. `displayName` is trimmed and bounded; the server generates the organization ID. The request requires `Idempotency-Key`; replay returns the original organization and key reuse with a different request returns 409. The transaction writes the organization, sole initial membership, creation idempotency record, hash-linked creation audit event, and outbox event atomically. Agent principals cannot create organizations. Migration `019_organization_onboarding.sql` adds the scoped creation-idempotency table.


### Automated invitation email (Phase 44)

Set `MANDATE_INVITATION_TOKEN_ENCRYPTION_KEY_HEX` to a randomly generated 32-byte key (64 hex characters) on both API and worker processes, injected from a secret manager; the worker additionally needs `MANDATE_INVITATION_EMAIL_FROM` and `MANDATE_INVITATION_ACCEPT_URL`. SES v2 uses the AWS SDK default credential chain and region; verify the sender identity and production sending mode in SES before enabling. The worker sends plain-text acceptance links with the token in the URL fragment, retries with capped exponential backoff (12 attempts maximum), records only coarse failures, cancels jobs for revoked/accepted/expired invitations, and erases ciphertext on terminal state. Delivery is at-least-once if SES accepts a message but the worker loses the response, so recipients may see a duplicate. Delivery tests use local PostgreSQL and a fake transport; tests do not send paid SES email. Drain pending jobs before rotating the symmetric key. OIDC remains the identity authority; IdP account provisioning is vendor-specific and remains deployment integration work.

### Organization invitations (Phase 32)

An OWNER or ADMIN can create an invitation with `POST /api/v1/orgs/{orgId}/invitations`; only an OWNER can invite another OWNER. The service returns a random 256-bit invitation token once, stores only its SHA-256 hash for acceptance, expires invitations after seven days, and saves the token-free replay response with the invitation. When configured, the API also encrypts the token with AES-256-GCM and inserts a durable email job in the invitation transaction; otherwise administrators deliver the returned token out of band. `POST /api/v1/invitations/accept` requires a valid human JWT with `email_verified: true`; the normalized signed email claim must match the invitation. Acceptance atomically creates membership and marks the invitation accepted, with hash-linked audit and outbox events. The `/api/v1/me` profile never returns the verified-email claim. Migration `020_organization_invitations.sql` stores invitation metadata and hashed tokens; migration `024_invitation_email_deliveries.sql` stores the optional encrypted delivery queue.

### Invitation administration (Phase 33)

`GET /api/v1/orgs/{orgId}/invitations` returns up to 100 newest invitations to OWNER/ADMIN members; the projection includes no email address or token. `DELETE /api/v1/orgs/{orgId}/invitations/{invitationId}` requires an idempotency key and revokes only a pending invitation. The store serializes revocation against other organization mutations, rechecks the administrator role in the transaction, and records the command-idempotency result plus audit/outbox events atomically. A revoked token cannot be accepted; accepted/expired/revoked invitations are not transitioned a second time.

### Organization team membership (Phase 29)

`GET /api/v1/orgs/{orgId}/members` returns tenant members to an authenticated member. `PUT /api/v1/orgs/{orgId}/members/{subject}` adds a subject or changes its role; `DELETE` removes the membership. Every mutation requires an `Idempotency-Key`. OWNER and ADMIN can manage members; only OWNER can grant or modify OWNER membership. Organization-row locking serializes owner changes, and the final OWNER cannot be demoted or removed. Writes commit membership, scoped idempotency response, hash-linked audit event, and outbox event in one PostgreSQL transaction. Member identity uses the OIDC `sub`; the API does not create or authenticate identity-provider accounts. A user gains access only when the authenticated OIDC subject matches the managed membership.

### MCP process (Phase 30)

`apps/mcp-server` runs as a local stdio MCP subprocess with the official TypeScript SDK. Start it with `npm run dev:mcp`; configure `MANDATE_API_URL` and an OIDC bearer or scoped agent bearer in ignored `.env.local`. The server calls `/api/v1/me` at startup, pins the organization to the authenticated agent identity or a configured human organization already present in that identity, and exposes no `orgId` tool argument. The backend REST API repeats all tenant, role, and action checks. Tools include policy list/get, deterministic action simulation, agent action request, action detail, and receipt lookup. No generic calldata execution, activation, approval, or revocation tool is published. MCP stdio output remains protocol-only; startup errors go to stderr.

```sh
cp .env.example .env.local
# Set MANDATE_API_TOKEN to an authenticated OIDC access token or scoped mnd_agent_ token.
# If the human token has several org memberships, set MANDATE_ORGANIZATION_ID to one of them.
npm run dev:mcp
```

`npm run dev:mcp:http` starts a separate hosted Streamable HTTP MCP resource server. It publishes RFC 9728 protected-resource metadata at `/.well-known/oauth-protected-resource/mcp`, points clients to `MANDATE_JWT_ISSUER`, and verifies each Bearer token through the existing `/api/v1/me` endpoint. Human JWTs must include the exact MCP resource URL in `aud`; configure the identity provider to mint that audience and set `MANDATE_JWT_AUDIENCE` to a comma-separated allowlist containing both the API audience and MCP resource URL (for example `mandate-api,https://api.example.com/mcp`). The API verifies signature, issuer, expiry, subject and audience before exposing identity, and the MCP resource check rejects tokens with a different audience. Scoped `mnd_agent_` credentials remain bound by the API to their agent and organization. The verified token is passed through the REST API for each MCP operation, where tenant, role, and policy enforcement remain authoritative. Set `MANDATE_MCP_RESOURCE_URL` to the public canonical `https://<host>/mcp`; set `MANDATE_MCP_ALLOWED_ORIGINS` to a comma-separated browser-origin allowlist (empty denies browser origins). A multi-organization human must configure a membership-verified `MANDATE_ORGANIZATION_ID`; agents are pinned to their authenticated organization. `MCP_PORT` defaults to 3100 and `HOST` defaults to `127.0.0.1`. Production must place the process behind a TLS-terminating proxy on a private network, preserve the public `Host`, and forward `X-Forwarded-Proto: https`. Hosted mode does not use a static `MANDATE_API_TOKEN`; model-provider API keys remain unrelated to MCP authentication.

### Policy activation plan (Phase 15)

`POST /api/v1/orgs/{orgId}/policies/{policyId}/activate` prepares and persists a deterministic owner-Safe transaction plan for the current draft revision. It requires an organization `OWNER`, an idempotency key, a verified active account, a currently valid on-chain Safe/guard/module relationship, and a supported policy revision. The API reads the Safe owner set, threshold, nonce, guard epoch, module agent-key version, and a pinned chain block; it returns the exact EIP-712 SafeTx payloads and digests. A new agent key is registered first when needed, then the policy hash and limits are configured in the guard.

This route does not sign or submit transactions and does not mark a policy/grant active. The response state is `AWAITING_SAFE_OWNER_SIGNATURES`; the Safe owners sign/execute the returned calls through their wallet. `POST .../activate/finalize` accepts the plan identifier and direct Safe transaction hashes; it verifies Safe `ExecutionSuccess` events, configured confirmation depth, canonical block hashes, and resulting guard revision hash/epoch and agent registration. Only then does one transaction mark the plan CONFIRMED and policy/grant ACTIVE while persisting receipt records, audit and outbox events. Configure `MANDATE_CHAIN_CONFIRMATIONS` as a chain-ID-to-confirmation-count JSON map; no implicit confirmation default is used by the API finalizer. If another Safe transaction advances the nonce first, the plan must be superseded/rebuilt by a later lifecycle operation; do not reuse stale SafeTx signatures. Migrations `009_policy_activation_plans.sql` and `010_policy_activation_finalization.sql` store plans, pending/active grant state, idempotency results, final receipt evidence, audit and outbox events transactionally.

For local/manual use, set `MANDATE_EVM_RPC_URLS` and `MANDATE_SAFE_SINGLETONS` in the API environment before activation; localhost HTTP RPCs are accepted only for local development and configured remote RPCs must use HTTPS. Never send Safe owner private keys to the API.

### Finalize policy activation (Phase 16)

`POST /api/v1/orgs/{orgId}/policies/{policyId}/activate/finalize` requires an OWNER, an idempotency key, the persisted activation-plan UUID, and the transaction hashes for the planned direct Safe calls in order. The API confirms that each transaction succeeded, was sent directly to the expected Safe, emitted exactly one matching `ExecutionSuccess` SafeTx hash, remains canonical at its receipt block, and meets the explicit confirmation count for its chain. It then reads the live guard revision hash/epoch and module key version/active flag. Only after all checks does one Postgres transaction move the plan to CONFIRMED, activate the policy/grant, store each final receipt, and append the audit/outbox records. Replays with the same key and transaction hashes return the persisted result; a changed request conflicts. The API accepts configured remote HTTPS RPCs and localhost HTTP for local testing. Set `MANDATE_CHAIN_CONFIRMATIONS` to a JSON map such as `{"10143":12}`; unspecified chains fail finalization closed.

### Policy revocation plan and finalization (Phase 17)

`POST /api/v1/orgs/{orgId}/policies/{policyId}/revoke` requires an OWNER, an idempotency key, an ACTIVE policy/grant, and a verified Safe enrollment. It reads current Safe owners, threshold, nonce, guard policy hash/epoch, and module state, then persists a single exact EIP-712 SafeTx call to `revokePolicy()` with an `AWAITING_SAFE_OWNER_SIGNATURES` lifecycle state. The policy/grant remain ACTIVE until the Safe owner threshold executes the call. `POST .../revoke/finalize` accepts the plan UUID and Safe transaction hash; it verifies successful direct Safe execution, the matching `ExecutionSuccess` hash, canonical receipt block, configured confirmation depth, and the disabled guard with the expected next epoch. One Postgres transaction then records the FINAL receipt, moves the plan to CONFIRMED, marks policy/grant REVOKED, and appends audit/outbox events. Same-key replays return the stored result; changed requests conflict. Confirmation depth comes from `MANDATE_CHAIN_CONFIRMATIONS`; unconfigured chains fail closed. Migration `011_policy_revocation_plans.sql` persists revocation plans and receipt evidence.


### Execution receipt reconciliation (Phase 23)

The worker also polls submitted attempts when both `MANDATE_EVM_RPC_URLS` and `MANDATE_CHAIN_CONFIRMATIONS` contain matching chain entries. It verifies configured chain identity, requested transaction hash, receipt block hash against the canonical block, and confirmations before treating a receipt as final. Before finality it stores a `TENTATIVE` receipt; a receipt that disappears before finality is marked `REORGED` and the action remains pending/submitted for re-inclusion. A final status-1 receipt atomically marks attempt `CONFIRMED`, action `RECONCILED`, receipt `FINAL`, and reservation `CONSUMED`; status 0 marks attempt `REVERTED`, action `RECONCILED`, receipt `FINAL`, and reservation `RELEASED`. Audit-chain/outbox events are committed in that same transaction and the alert worker projects reconciliation/reorg notifications. Migration `014_execution_reconciliation.sql` adds indexes for polling and receipt activity reads. Receipt records omit transaction input/calldata and retain only receipt metadata needed for evidence.

The worker can still run in outbox-only mode when both chain maps are empty. To enable execution reconciliation, configure both maps with identical chain keys and an explicit 1–10000 confirmation depth for each chain; unmatched maps fail startup. Example values are in `.env.example`. The current receipt poller recovers exact canonical replacements and classifies a dropped submission only when caller-signed sender/nonce metadata, a hash-verified finalized checkpoint after authorization expiry, complete persisted indexer coverage from the authorization snapshot, and absence of an exact execution event all agree. Legacy records lacking submission metadata or a persisted indexer coverage boundary remain pending. Deep-reorg detection now checks settled receipts against the live canonical hash and DB indexer finality; a verified mismatch marks the action/attempt/receipt REORGED, reactivates its reservation hold, pauses the account, and emits hash-linked incident events. The owner-only reorg-resolution route records the reservation disposition without changing REORGED evidence or reactivating the account. Account verification is a separate explicit step and is rejected until every deep-reorg reservation for that account has an owner disposition.

Optionally configure `MANDATE_RECEIPT_RPC_FALLBACK_URLS` as a chain-ID-to-ordered-array JSON map (one to three HTTPS endpoints per configured primary; loopback HTTP is accepted for local tests). The worker probes every endpoint's chain ID before use, skips unavailable or mismatched endpoints, and sequentially retries read calls on the remaining verified endpoints. Empty receipt/block reads also try the next endpoint so lagging providers do not prematurely report missing evidence. This setting affects receipt reconciliation reads only; transaction broadcasting is not retried through it. As with indexer RPC failover, matching chain IDs do not prove provider independence or canonical history, so reconciliation still compares receipt and block hashes and operators must assess provider independence.


### Fee-replaced execution transactions (Phase 24)

When an attempt's submitted transaction hash has no receipt, the reconciler checks the finalized indexer's canonical logs for `AgentActionExecuted` at the exact authorized module, agent address, key version, module nonce, and typed action hash. Only a full match may select an alternate transaction hash. The worker then verifies that transaction's live receipt and finality through the configured chain RPC; after finality it records the actual mined hash on the execution attempt, the receipt projection, a replacement audit event, and the normal settlement events. The original hash remains in the idempotency submission row as the bytes originally accepted. This covers fee-bumped replacements that preserve and execute the exact signed module call without ever persisting transaction bytes. Missing receipts without such canonical event evidence remain pending; automatic `DROPPED` classification and deep post-finality reorg compensation are implemented. Phase 41 adds the owner recovery lifecycle below.

### Deep-reorg operator resolution (Phase 41)

After a finalized receipt is proven non-canonical, the reconciler preserves the action, attempt, and receipt as `REORGED`, restores the budget reservation to `ACTIVE`, pauses the account, and emits the incident evidence. An authenticated organization OWNER can call `POST /api/v1/orgs/{orgId}/actions/{actionId}/reorg-resolution` with an `Idempotency-Key` and `{ "disposition": "CONSUMED" | "RELEASED", "reason": "...", "evidenceHash": "0x..." }` (the evidence hash is optional). PostgreSQL rechecks OWNER membership and lifecycle state under transaction locks. A single append-only resolution records the original and canonical block hashes, block number, actor, decision, reason, and optional evidence hash; the same transaction updates only the reservation, appends the hash-linked audit event and outbox event, and persists an indefinite idempotency result. Replays of the same key/input return `200`; conflicting or racing decisions return `409`; non-owners receive `403`. The action/attempt/receipt remain `REORGED` and the account remains `PAUSED`; neither this endpoint nor the SDK operation reactivates the account or resubmits a transaction. Account verification is rejected while any of the account's deep-reorg reservations remains unresolved; after all holds receive explicit owner dispositions, use the separate verification route to recover account status following operational checks.

The TypeScript SDK exposes `resolveDeepReorg(actionId, disposition, reason, idempotencyKey, evidenceHash?)`. Migration `022_execution_reorg_resolutions.sql` enforces one append-only resolution per action and immutable database rows. Unit tests, a real-PostgreSQL concurrency/replay integration test, and an API integration test cover owner authorization, invalid requests, conflict handling, audit and state preservation.

### Shared API rate limiting (Phase 35)

The API applies a PostgreSQL-backed atomic fixed-window limit to `/api/v1/*` requests (except OpenAPI), defaulting to 120 requests per source IP per 60 seconds. PostgreSQL is shared coordination across API replicas; request counts use an UPSERT so concurrent requests cannot exceed the window through a read/modify/write race. Responses include `RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset`, and `Retry-After` when exhausted, with a typed `429 RATE_LIMITED` error. Health endpoints remain available for probes. Only an HMAC-SHA-256 subject digest is stored; production must configure the same random `MANDATE_RATE_LIMIT_HMAC_KEY` (at least 32 bytes) on each replica. Local development generates an ephemeral process key. Stale windows are opportunistically pruned.

### TypeScript SDK and CLI (Phase 37)

`packages/sdk/src/index.ts` exports `MandateClient`, a Node 22+ REST client that discovers the authenticated human/agent identity from `/api/v1/me`, validates explicit tenant selection against that identity, and invokes the same REST routes used by MCP. Human identities with no organization can create one and then call `selectOrganization`; multi-organization identities must select a membership explicitly. SDK operations now cover every business operation documented in the current OpenAPI document: onboarding/invitations/members, accounts, agents, policy draft/revision/activation/revocation, simulation/actions, audit/receipts/alerts, webhooks, and model-provider credential lifecycle. It performs no policy evaluation or authorization locally. `MandateApiError` exposes the API error code, HTTP status, request ID, and `Retry-After` value without attaching raw response bodies. API keys/tokens remain runtime inputs and are never logged by the SDK.

```ts
import { MandateClient } from './packages/sdk/src/index.js';

const apiUrl = process.env.MANDATE_API_URL;
const token = process.env.MANDATE_API_TOKEN;
if (apiUrl === undefined || token === undefined) throw new Error('Configure Mandate API URL and token');
const client = await MandateClient.connect({
  apiUrl,
  token,
  ...(process.env.MANDATE_ORGANIZATION_ID === undefined ? {} : { organizationId: process.env.MANDATE_ORGANIZATION_ID }),

const policies = await client.listPolicies();

It uses `MANDATE_API_URL`, `MANDATE_API_TOKEN`, and optional `MANDATE_ORGANIZATION_ID`; action JSON is schema-validated before it is sent to the API. `organizations create <name>` supports first-time human onboarding with no existing tenant. `invitations accept <@file|->` accepts a verified-email invitation without placing its one-time token in shell history. `model-providers list|set|test|disable|delete` manages optional organization model-provider credentials through the existing API. ### Signed audit exports (Phase 42)

`GET /api/v1/orgs/{orgId}/audit-exports?limit=1000&beforeSequence=...` creates an OWNER/ADMIN-only Ed25519-signed export, with ascending event order, the original event hash links, canonical JSON bytes, key ID, public-key fingerprint, and an explicit integrity notice. The endpoint is backed by the same tenant-scoped PostgreSQL audit projection; exports are bounded to 10,000 events. Agents and lower-privilege members are denied. An unset signing key returns `503 DEPENDENCY_UNAVAILABLE`. The SDK exposes `getSignedAuditExport()` for human clients.

Configure `MANDATE_AUDIT_SIGNING_SECRET_ARN` on the API process to an AWS Secrets Manager secret whose JSON value has exactly `keyId` and `privateKeyPem` fields. Use an Ed25519 PKCS#8 private key and restrict the API task role to read that secret only. The API loads the key at startup; the endpoint does not accept a signing key from a caller. A verifier must compare the export's `keyFingerprint` with a fingerprint pinned through a separate trusted channel, then verify the signature and internal links with `verifyAuditExport(export, trustedFingerprint)` from `packages/application/src/audit-export-service.ts`. The embedded public key alone is not a trust anchor. A valid signature proves that this key signed these bytes; it does not prove the source facts are truthful or the exported history is complete.

### Periodic audit anchors (Phase 43)

The worker can periodically anchor each organization's current hash-chained audit head to S3 Object Lock. Set `MANDATE_AUDIT_ANCHOR_BUCKET`, `MANDATE_AUDIT_ANCHOR_RETENTION_DAYS`, and the same `MANDATE_AUDIT_SIGNING_SECRET_ARN` on the worker. The optional `MANDATE_AUDIT_ANCHOR_INTERVAL_MS` (default 60,000; range 1,000–86,400,000) and `MANDATE_AUDIT_ANCHOR_BATCH_SIZE` (default 25; range 1–500) bound the cadence and work. With no bucket configured, anchoring is disabled and the worker runs normally.

Before enabling it, provision a bucket with versioning and Object Lock enabled, configure a retention policy that permits the requested COMPLIANCE retention, and administer it separately from the PostgreSQL account (preferably a separate AWS account). The worker writes canonical, domain-separated Ed25519-signed checkpoints using conditional create (`If-None-Match: *`), requires S3 version IDs, and records immutable checkpoint metadata in PostgreSQL. The per-organization checkpoint chain and DB advisory lock prevent duplicate/concurrent checkpoint rows. Configure the worker role for only `s3:PutObject`, `s3:PutObjectRetention`, `s3:GetObject`, `s3:GetObjectRetention`, and `secretsmanager:GetSecretValue` on the anchor prefix/key; the bucket must not be writable by the API or application users. Provisioning, exact IAM policy, cross-account separation, and a live AWS test remain deployment gates. AWS requires versioning for Object Lock and `s3:PutObjectRetention` for per-object retention [Object Lock guide](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html), [S3 permissions](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-with-s3-policy-actions.html). Signed export and anchor signatures use different signing domains. Verify downloaded objects offline with `npm run audit-anchor:verify -- --file <path> --trusted-fingerprint <sha256> --checkpoint-hash <sha256> [--previous-checkpoint-hash <sha256|none>]`; provide the expected object hash from its immutable key or trusted checkpoint record, pin the fingerprint out of band, and use the previous-hash option when checking a checkpoint chain.
